# Read-only DAG structural audit protocol — 2026-11-03

Purpose: use **actual parsed Pegasus DAX nodes and edges** rather than filename tokens. On the frozen v17 confirmation archive, `Epigenomics_46.xml` is in fact **47** jobs; `Sipht_100.xml` is **97**, and `Sipht_60.xml` is **58**. Counts are crossed against `jobCount` and actual `<job>` elements. This resolves sample-size descriptions, not any changed simulator outcome.

The analyzer is separate from the optimizer. It reads DAX XML but does NOT invoke WorkflowSim, target fitness evaluation, VM optimizers, random numbers, or Github network. It rejects missing/duplicate jobs, missing dependency refs, duplicate edges, cycles, nonfinite/negative runtime/file sizes, and mismatched DAX jobCount/childCount metadata. It computes deterministic root/sink counts, edges, join/fork tasks, longest path by **DAX-provided unscaled runtimes**, critical-runtime share, work/span ratio, maximum topological layer width and edge overlap of referenced output/input files.

**Do not interpret** DAX file sizes as observed inter-VM network communication; a repeated file can be cached and on the same VM. `declared_intertask_file_bytes` sums producer output sizes on each dependency edge with a common input filename, is a *logical edge-file-volume proxy*, and can count one file on multiple fanout edges. DAX runtime-weighted critical path is NOT a calibrated WorkflowSim time bound because VM speeds and transfer/storage costs differ. Missing shared-file intersections are explicitly counted.

The report join uses only original archived primary-reference `v17_confirm_cases.csv` from GitHub Actions run `41626382711` and optional pilot reference rows from `41625790444`. Descriptive comparisons by family/VM speed can be reported, but because v17, its DO rule and existing DAX families were repeatedly studied and labels are already known, **do not** choose a feature threshold / predictor on this joined outcome data and call it prospective evidence. With just four family clusters, correlation/feature selection would be deeply underpowered and leak labels into any subsequent 'holdout' if reused.

Next credible validation requires selecting and freezing truly independent DAG families / generated topologies and seeds BEFORE running the candidate algorithms, and reporting planned/simulator model mismatch and wall-clock runtime as well as K16 actual Pareto HV. The parser alone does not create such a holdout and cannot prove a publishable v17 advantage.
