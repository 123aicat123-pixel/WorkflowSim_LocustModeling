# v14 true-planned-timeline paired offspring search: frozen development protocol

Experimental and opt-in only. The original v12 is unchanged and is compared alongside the v14 RANDOM PAIRED reproduction control and equally cost-seeded NSGA-II.

Version 14 changes the *search* process. Each generation of 30 target objective evaluations yields 16 normal v12-type offspring and 14 one-step neighbors of the immediately preceding normal offspring, paired within the existing FLA makespan/cost subpopulations. Every genotype still gets EXACTLY one true StageInAwareScheduleEvaluator objective evaluation. The first child of each pair is evaluated with a detached **real stage-in-aware PLANNING time-axis** snapshot generated in the same call (one objective evaluation, no hidden probe). The second child changes one eligible task VM gene, chosen either from that last-finishing task's predicted calendar (v14-timelinepair) or uniformly at random among tasks and feasible alternative VMs (v14-randompair). All evaluated children are kept eligible for planned Pareto archive/survivor selection, including dominated trials. The equal 3030 evaluation count includes the original 30 population initialization and 3000 child or local-probe evaluations. The paired control removes the false advantage of reallocating ordinary independent offspring into neighborhood evaluations.

Stage-in aware trace is a model estimate, not literal WorkflowSim simulator observation. It returns start/finish snapshots with the same stage-in-aware objective evaluation that is already counted. A fast local gap test approximates a new VM's earliest free insertion, using optimistic service and existing VM occupied intervals; it does NOT claim that downstream DAG timing or replica caching stays unchanged. Only the second normal counted evaluator call establishes the modified genome's new planned makespan and cost.

Research question: does informed, exactly-budgeted local neighborhood search improve **simulator** Pareto coverage relative to both v12 and budget-matched random-pair search, rather than merely shifting search breadth? Development pilot: Montage_50, CyberShake_50, Sipht_60 × VM speeds default/staggered × paired seeds 151/152; 4 algorithms each, pop=30, generations=100, equal cost seeded initialization, exact 3030 planner evaluations and exactly K=16 true WorkflowSim replays using original pareto-cover policy. Primary HV reference 1.5 × coordinatewise maximum of PLANNED selected K16 makespan/cost across all algorithms/seeds within a workflow/speed +1; 3.0× secondary. Fail, do not fix, if any actual simulator point exceeds frozen reference. Record negative and family-level outcomes, runtime and every offspring counter. These are previously studied workflow families: DEVELOPMENT ONLY. Do not promote on a positive pilot without new independent DAG/family validation.
